## 2. 圏の決め方

順位は距離ではなく「レース日にサーキットへたどり着ける確実さ」。
判断材料は 2 つだけに絞ってある。

1. **宿⇄サーキットを5回走る**（金の宿入り＋土往復＋日往復）。ここが最大の差
2. **土日の渋滞の向き**。名古屋側（東名阪 四日市IC〜鈴鹿IC）は渋滞の本流、
   南（伊勢道を北上）は逆向きなので同じ距離でも時間が読める

除外した材料:

- **往路（豊洲→鈴鹿 約400km）**: 金曜に先にサーキットへ寄るので宿の位置に関係なく共通。
  「鈴鹿の手前か奥か」も同じ理由で効かない
- **月曜の帰路**: 帰るだけで時間の制約がないため、距離差は順位に入れない

結果:

圏は**サーキットまでの所要時間**順。豊橋に保険があるので、そこより遠いエリアは検索しない。
楽天のエリア区分は粗く、**鈴鹿・亀山は「津」に、桑名・長島・湯の山は「四日市」に含まれる**。

## 2-2. 通知の条件

`[notify.filter]` で絞る。state には全件残るので、条件を緩めればその時点で新規として通知される。

| 条件 | 値 | 理由 |
|---|---|---|
| parties | 4人1室 / 4人2室 | 親子2人は保険用で、通知するほどではない |
| nights | 3泊 | 金→月が本命 |
| max_tier | 3 | 現状は全エリアが圏3以内。圏4 を足したときの保険として残してある |
| max_total_price | 110,000円 | 滞在合計・全室分 |
| 圏1・圏2 の上限 | 150,000円 | 近くて代えが効かないので、高くても見逃さない |
| include_unknown_price | false | 料金が読めないものは出さない。11/1 が近づいたら true に戻す |

## 2-3. 名指しで見る宿

楽天のエリア検索は**空室のある宿しか返さない**ので、満室・未発売の宿はいくら待っても出てこない。
`[[rakuten.watch_hotels]]` に宿番号を書くと `hotelNo` で直接引くので、空いた瞬間に拾える。
満室のあいだは 404 not_found が返るだけでエラーにはならない。

## 5. 既知の落とし穴

- **楽天の料金**: `dailyCharge` は初日分しか返らないことが多い。1泊単価×泊数で概算し、
  その場合は `≈` を付ける。2026-09-18 以前のログは修正前のコードなので料金列が信用できない
  （泊数を減らすと合計が上がる、という矛盾が出ている）
- **URL は自分で組み立てない**。楽天サイトへ到達できないので形式を検証できない。
  `run --links` が API の返した値をそのまま出すので、リンクはそこから取る
- **チャットに裸のURLを貼ると後続の文章まで飲み込まれる**ことがある。コードブロックに入れる
- **ntfy は本文 4096 バイトで 413**。`[notify.filter]` で絞る前提の設計
- **ntfy に本文なしで POST すると「Triggered」とだけ表示される**。
  差分があっても `[notify.filter]` で全部落ちると本文が空になるので、送る前に必ず確認する
